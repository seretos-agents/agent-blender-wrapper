# agent-blender-wrapper

Pure skill plugin — no binary of its own. It wraps the **external BlenderMCP server** ([ahujasid/blender-mcp](https://github.com/ahujasid/blender-mcp), MIT): the MCP is declared inline in the `mcpServers` block of **both** `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json`, and `skills/blender-wrapper/SKILL.md` teaches the agent when and how to drive it. The host agent launches the server automatically via `uvx`.

## Contracts an agent won't infer from the tree

- **Three processes must be up, and only one of them is ours.** The MCP server is a thin TCP bridge: it forwards tool calls to a **BlenderMCP addon** running inside a live Blender GUI session on `localhost:9876`. The addon is installed by the user in Blender (Preferences → Add-ons → install `addon.py`) and must be started per session via "Connect to Claude" in the 3D View sidebar. Nothing in this repo can install, start, or health-check that half — if the addon isn't connected, every tool fails and the fix is always user-side. `BLENDER_HOST` / `BLENDER_PORT` override the socket target if the user changed the port in the addon.
- **Telemetry is deliberately disabled.** blender-mcp ships telemetry **opt-out**: without intervention it posts session UUIDs, tool names, timings, errors, and platform/Blender versions to a third-party Supabase endpoint. Both manifests therefore set `BLENDER_MCP_DISABLE_TELEMETRY=true` in the server's `env`. This is an intentional deviation from the "no `env` block" scaffold default — drop the block to re-enable telemetry. Note that the manifest `env` **wins over the user's own environment**, so a user who wants telemetry on must edit the manifest, not just set a variable. The server also accepts `DISABLE_TELEMETRY` and `MCP_DISABLE_TELEMETRY`; one is enough.
- **The version pin is exact on purpose.** `blender-mcp==1.8.0` in both manifests lets `uvx` reuse the same cached tool environment on every start instead of re-resolving against the index — the same cold-start reasoning as `agent-serena-wrapper`. Bumping it means editing both manifests **and** re-checking the tool inventory in `SKILL.md`: the upstream tool surface changes between minor versions (Hunyuan3D arrived that way).
- **`SKILL.md`'s tool inventory is hand-maintained against upstream.** It documents 22 tools across four groups (core/PolyHaven/Sketchfab/Hyper3D/Hunyuan3D) and — importantly — the *absence* of typed create/modify tools: geometry, transforms, materials and lights all go through `execute_blender_code`. If upstream adds first-class object tools, that framing in `SKILL.md` becomes wrong, not just incomplete.
- **`execute_blender_code` is the plugin's whole risk surface.** It executes arbitrary Python with full `bpy` access inside the user's Blender — filesystem reach included. The skill's Pitfalls section carries the mitigations (small single-purpose calls, no unrequested destructive ops, confirm before discarding work); keep them there rather than assuming host-level permission gating catches it.
- **Release is orphan-branch + marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version into both manifests, force-pushes an orphan `release` branch holding only install-ready files, and POSTs a dispatch (`category: skill`, `tags: ["3d","creative"]`) to BOTH `seretos-agents/modular-software-factory-staging` (lands straight to main there, no review) and `seretos-agents/modular-software-factory` (opens a review PR there). `main` and `release` share no history. Clients install at the tag `agent-blender-wrapper--vX.Y.Z`.
- **Required secret:** `MARKETPLACE_DISPATCH_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on both `seretos-agents/modular-software-factory` and `seretos-agents/modular-software-factory-staging`.
- **`assets/icon.png` and `description.md` are release artifacts, not just repo files.** The dispatch payload sends `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` and `.../description.md`, so both must live on the orphan `release` branch at the tagged commit — `release.yml`'s stage step copies them in for exactly that reason. Ship a real icon before cutting v0.0.1 or the listing has no image.
- **Depending on an MCP plugin:** declare it under `dependencies` in `.claude-plugin/plugin.json` (`{ "name": "agent-<mcp>", "version": ">=0.0.1 <1.0.0" }`). BlenderMCP is wired directly via `mcpServers` in both manifests (not via `dependencies`), which is why `dependencies` stays `[]`.
- **This repo ships TWO skills with deliberately disjoint triggers.** `blender-wrapper` drives a live Blender session; `blender-game-export` covers getting a finished asset out of Blender into a game engine (FBX settings, axis/unit conversion, verification) and is scoped to general export knowledge only — no project- or kit-specific conventions. `lint.yml` validates every `skills/*/SKILL.md` via `scripts/check_skills.py`, which also asserts each skill's frontmatter `name` equals its directory name and compiles every fenced ```python block in the file — a new skill directory without a matching, valid `SKILL.md` fails CI, it doesn't silently pass. `blender-game-export`'s numbers (the 270.02° rotation figure, the `(-bx, bz, -by)` axis mapping) were measured against Unity's actual FBX importer, not derived from documentation, and its bundled verifier (`skills/blender-game-export/scripts/verify_fbx.py`) only understands **binary FBX 7.x** — it refuses ASCII FBX and non-FBX input rather than mis-parsing it.
